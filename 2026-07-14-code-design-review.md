# Code design review — 2026-07-14

## Findings

1. **The advertised Pi CLI pass-through accepts options it does not honor.** `README.md:12-16` promises Pi-equivalent behavior, and `runner.ts:159-212` recognizes the full CLI snapshot. But `resolveForwardedOptions()` only applies model, thinking, tools, and resources at `runner.ts:403-425`. Options including `--api-key`, `--name`, `--session`, `--continue`, `--resume`, and `--approve` are accepted and resolve to `{}`. Replace the snapshot with one declarative table containing only SDK-backed child options; explicitly reject incompatible process/session options. That would also collapse much of the parser/spec/test burden.

2. **The extension bypasses the dependency graph with machine-specific imports.** `runner.ts:3-14`, `shared.ts:3`, `transcript.ts:1`, and `widget.ts:1-13` hard-code `/opt/homebrew/...`, including a nested `node_modules` path. This prevents loading under another Pi installation layout and silently uses global SDK `0.80.7` while `agent/package.json:15` declares `0.74.x`. Update the declared dependencies and use the same public package imports as neighboring extensions.

## Maybes - need to verify whether true at all before acting on

3. **Cancelling during startup may still launch the agent.** The UI sets `aborted` at `widget.ts:267-270`. Once session creation finishes, `runner.ts:490` calls `abort()` while the session is idle, then continues through extension binding and `session.prompt()` at `runner.ts:493-504`; Pi’s abort does not appear to be sticky. Shutdown may have the same race at `index.ts:31-35`. If this reading is correct, a cancellation signal carried through startup could stop before binding or prompting whenever cancellation or shutdown was requested.

4. **Inherited history may sit outside the child’s `SessionManager`.** Parent messages are cloned at `runner.ts:452-454`, but the child is created with an empty manager at `runner.ts:477-485`. Extensions are then bound—emitting `session_start`—before messages are assigned directly to agent state at `runner.ts:493-498`. If the SDK expects the manager and agent state to remain aligned, child extensions may see empty history and SDK operations that rebuild context from the manager, notably compaction, may omit inherited messages. It may be worth verifying whether the child session manager can instead be seeded before constructing and binding the session.

5. **Child resource-load failures may be silently ignored.** Resource options are mapped at `runner.ts:428-440`, but the diagnostics returned by `createAgentSessionServices()` and extension-loader errors do not appear to be inspected at `runner.ts:468-485`. For example, `--extension /missing/path` may proceed without that extension. If that behavior is undesirable, the child setup could collect diagnostics before session creation, report warnings, and fail on errors as Pi’s main CLI does.

6. **Completed-agent UI state may lack a bounded lifecycle.** Every completion clones and retains its full transcript in `completedAgents` at `widget.ts:47,61-75`. The 100ms interval started at `widget.ts:79-81` stops only when all completed cards are manually dismissed (`widget.ts:84-114,273-293`), so an idle completed card may force TUI renders at 10Hz indefinitely. If this is confirmed in normal use, completed entries could be capped and the timer could stop as soon as no agent is running; completed entries appear to need only event-driven renders.
